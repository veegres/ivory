# Repository Guidelines

## Project Structure & Module Organization
Ivory is split into a Go backend in `server/` and a Rsbuild/React frontend in `app/`. Backend packages are organized by concern: `features/` for business logic, `clients/` for integrations, `storage/` for persistence, and `core/` for wiring. Frontend source lives in `app/`, with `features/` for domain logic, `core/` for main pages and widgets, `shared/` for shared components, hooks, and providers, and `tools/` for standalone utilities (e.g. `pg_compacttable`). Tests live in `server/**/_test.go`, and on the frontend are colocated with the source they test (`[filename].test.[ext]`). Docs and screenshots are under `.doc/`; local Docker setups are under `.docker/`.

**Mandatory Check**: When modifying frontend code, always run `cd app && npm run lint` and `cd app && npm run build` to ensure no linting or TypeScript compilation errors were introduced.

## Build, Test, and Development Commands
Backend:
- `make -C server build` builds `server/build/ivory`.
- `make -C server test` runs `go test ./...`.
- `make -C server start` runs the built backend binary.

Frontend:
- `cd app && npm install` installs dependencies.
- `cd app && npm start` starts the Rsbuild dev server.
- `cd app && npm run build` runs TypeScript compile plus production build.
- `cd app && npm run lint` runs Rslint over `core/`, `features/`, `shared/` and `tools/`.
- `cd app && npm test` runs the Rstest suite once.

Use `.docker/ivory-dev/` for the stack.

**Keep the lint script's directory list in sync**: `lint`/`lint:fix` in `app/package.json` explicitly list which top-level directories Rslint scans. Any new top-level frontend directory (like `tools/`) must be added to both scripts, or its files are silently unlinted — CI's `npm run lint` step will report success even with real errors (e.g. unsorted imports) inside the missing directory.

## Architectural Patterns
- **Vertical Consolidation**: Prefer grouping all management logic for a single entity into one feature. For example, the `node` feature manages both Platform access (metrics, deployment operations) and the Database/Keeper (HA, config).
- **Service Splitting**: To keep code manageable, split large services by concern using a `service_<domain>.go` naming convention (e.g., `service_db.go` and `service_host.go`).
- **Generic Clients**: Centralize transport-level logic in generic clients (like `clients/http` or `clients/ssh`) and keep domain-specific logic in wrappers or consumers.
- **Platform Integration Boundary**: Keep `plugins/platform` generic. Platform adapters model deployment and troubleshooting primitives for a target platform, not Ivory-specific database behavior. Database-specific interpretation belongs in features such as `features/cluster`.

## File Naming Conventions
- **Go — Package Prefix**: Every Go source file (including `_test.go` files) is prefixed with its own package/directory name, e.g. `auth/model.go` → `auth/auth_model.go`, `node/service_keeper.go` → `node/node_service_keeper.go`. This applies uniformly, including files that already follow the `service_<domain>.go` split-by-concern pattern — the domain suffix and the package prefix serve different purposes (one disambiguates concerns within a package, the other disambiguates the file across the whole repo). Exception: `main.go` (standard Go entrypoint, always unique). `server/plugins/platform/docker/docker_system.go` / `docker_container.go` follow the rule like every other file — the `docker` prefix disambiguates them across the repo, and the `system`/`container` suffix happens to also name the `System`/`Container` interfaces they implement (see Platform Architecture above).
- **Frontend — PascalCase Everywhere**: All frontend files, `.ts` and `.tsx` alike, use PascalCase, matching the convention already used for components. Generic API filenames (`hook.ts`, `router.ts`, `type.ts`) are prefixed with their owning feature/module name, e.g. `features/auth/api/hook.ts` → `features/auth/api/AuthHook.ts`, `tools/pg_compacttable/api/job/hook.ts` → `tools/pg_compacttable/api/job/PgCompactTableJobHook.ts`. Root-level, non-colliding files just get PascalCased (`features/api.ts` → `features/Api.ts`, `shared/test/setup.ts` → `shared/test/TestSetup.ts`).

## Feature API Boundary (Frontend)
Each frontend feature exposes its own types in `features/<name>/api/<Name>Type.ts`. Types must live in the feature that owns them — never in a shared "plugins" or "common" file. Cross-feature imports are allowed only in the consuming direction (e.g., `cluster` may import from `node` and `query`; `query` and `node` must not import from `cluster`).

Current ownership:
- `KeeperPlugin` enum → `features/node/api/NodeType.ts` (keeper plugin selector is a node-level concept)
- `DbPlugin` enum → `features/query/api/QueryType.ts` (database engine type is part of the DB connection config)
- `DbConfig` interface → `features/query/api/QueryType.ts` (database connection config belongs to the query feature)

Backend mirrors this: `server/features/node/node_model.go` defines `KeeperPlugin = keeper.Plugin` (alias); `server/features/query/query_model.go` defines `DbPlugin = database.Plugin` (alias) and `DbConfig` struct. Plugin packages (`server/plugins/*`) are internal implementation details — features expose their own types and use mapper functions to translate to/from plugin types at the boundary.

## Backend Model & Service Conventions
- **Models Live in `_model.go`**: Every domain struct — requests, responses, criteria/filter structs, DTOs — belongs in the feature's `<feature>_model.go`, never in a `_service*.go`, `_repository.go`, or `_router.go` file, even when the type is only used by one of those files. The single exception is the core type a file is built around: `Service` stays in `<feature>_service.go`, `Repository` in `<feature>_repository.go`, `Router` in `<feature>_router.go` — those aren't domain models, they're the file's own scaffolding. For example, `cluster.SearchRequest`/`cluster.SearchCriteria` used to sit in `cluster_service_crud.go`/`cluster_repository.go` next to the `Search` methods that use them; they were moved into `cluster_model.go` alongside `Request`/`Response`/`NodeConfig`.
- **Mappers Live in `_model.go` Too**: Conversion/mapper functions between types (`mapXxx`, `xxxToYyy`, `xxxFromYyy`) belong in the model file next to the types they convert. This holds even when the mapper is only called from a service file elsewhere in the same package, e.g. `mapPlanNodeConfigs` moved from `cluster_service_deploy.go` into `cluster_model.go`.
- **A Mapper Is a Method When Its Input Type Is Local, Otherwise a Free Function**: Go has no extension methods — a method's receiver must be a type owned by the same package, so a mapper can only become `func (m Model) toOther() Other` when `Model` is defined in that package; the *output* type can be anything. Most boundary mappers in this codebase go the other direction (a foreign plugin/feature type in, a local model out — e.g. `mapKeeperResponse(r node.KeeperOneResponse) NodeConfig` in `cluster_model.go`, or every `*ToBackupV1` export mapper in `backup_model_v1.go` taking a foreign `cluster.Response`/`query.Response`/`permission.UserPermissions`) and so must stay free functions. Where the input type is local, make it a method: `backupClusterV1.toCluster()`, `backupQueryV1.toQuery()`, `backupPermissionsV1.toUserPermissions()`, `query.DbConfig.toDatabaseConfig()`, and `query.DbOptions.toQueryOptions()` are all methods for exactly this reason (their receiver type is defined in the same package as the method). `syncPermissionV1(p string)` in `backup_model_v1.go` stays free regardless — its input is the builtin `string`, not a named local type, so there is no type to attach a method to.
- **Other Free Functions Become Service/Repository Methods**: Outside of model-file mappers, a standalone (non-method) function living in a feature's service/repository files should be a method on that file's core type instead — e.g. `hasLeaderEntry` (`cluster_service_discovery.go`), `matchesPlugin` (`query_repository_crud.go`), and `buildNodeValues` (`node_service_keeper_deploy.go`) were all converted from free functions to `Service`/`Repository` methods. This keeps a feature's behavior discoverable through its core type rather than scattered as package-level helpers. The one exception is a function that takes its own type parameters (`func foo[T any](...)`) — Go does not allow methods to introduce new type parameters, so generic request-handling helpers like `node_router.go`'s `handleKeeperParamRequest[T any]` must stay free functions.

## Platform Architecture
- **Platform Package**: `server/plugins/platform` is the backend integration point for deployment targets. Existing implementations live under `server/plugins/platform/<adapter>/`, for example `docker/`. Future adapters such as Kubernetes or OpenShift should be added as sibling packages.
- **Platform vs Transport**: Platform is the product-level abstraction. SSH is only a transport/client detail for the Docker adapter and credential flow. Keep names like `clients/ssh`, `sshPort`, `SSH_KEY`, and SSH credential UI labels when they describe the actual transport or stored credential type.
- **Docker Plugin**: `platform/docker` implements platform deployment operations for on-prem Linux hosts by executing Docker commands over SSH. It is split into exactly two implementation files by interface: `docker_system.go` for `System` methods (node metrics, logs, process listing, SSH key provisioning) and `docker_container.go` for `Container` methods (container lifecycle and container metrics). Docker command helpers and tests may still use Docker-specific names internally when they are truly Docker CLI details.
- **Generic Platform Methods**: Platform adapters expose generic deployment operations: `KeeperNodeList`, `KeeperDeploy`, `KeeperStop`, `KeeperDelete`, and `KeeperLogs`, returning `OperationResult`. Do not name these methods after Docker containers, Kubernetes pods, or databases.
- **OperationResult**: Use `OperationResult` for command/API execution output with `stdout`, `stderr`, and `exitCode`. It is intentionally not called Container, Pod, Workload, or Database because it is only an operation result.
- **Node Platform Boundary**: The node feature uses prefixed service methods such as `PlatformContainerUp`, `PlatformContainerStop`, `PlatformContainerStart`, `PlatformContainerDown`, `PlatformContainerList`, and `PlatformContainerLogs` to avoid collisions with existing Keeper methods like `KeeperNodeList`, and `PlatformSystemMetrics`/`PlatformSystemProcesses`/`PlatformSystemInfo`/`PlatformSystemLogs`/`PlatformSystemCopyId` for the node's own system. Frontend node APIs mirror this as `NodeApi.container.*`/`NodeApi.system.*`, `useRouterNodePlatform*` and `useRouterNodeSystem*`.
- **System Is the Node Itself, Platform Is the Target**: `platform.System` covers the node a deployment lands on (its metrics, processes, logs, `authorized_keys`), `platform.Container` covers the things deployed onto it. There is no wrapping `Adapter` interface bundling the two — `platform.Plugin` embeds `System`, `Container` and `Metadata` directly, since the wrapper added nothing over listing them. The UI names that split the same way — the **System** tab (`features/node/component/system/`) against the **Container** tab — so "platform" stays the name of the target, never of one of its two halves.
- **Platform Metadata**: `platform.Metadata` is a separate interface from `platform.System`/`platform.Container`, exactly as `keeper.Metadata` is from `keeper.Adapter`: System and Container together cover operations against a reachable node, Metadata covers what the platform can be asked for at all. All three are registered together as `platform.Plugin` (see **One Plugin, One Registry**). It carries `SupportedFeatures()` only. Docker declares `ViewNodeSystem`/`ManageNodeSystem` true because it runs containers on a host Ivory reaches over ssh; a platform that only ever addresses a scheduler declares them false and the System tab disappears rather than erroring. `cluster.Service.getSupportedFeatures` merges the platform's map alongside the keeper's and the database's, so the gate rides the existing `Overview.features` → `useHasAccess` path — and `NodeMainTabsHead` hides the tab on `"unsupported"` only, never on `"denied"`, which the tab body still reports. A cluster names no platform of its own yet, so it reports `node.DefaultPlatform`'s capabilities (the same fallback `PlatformVaultConnection.PlatformOrDefault` applies).
- **Routes and Features**: Platform routes live under `/node/platform/...`, split into the node's own system (`/node/platform/system/metrics`, `/system/logs`, `/system/processes`, `/system/info`, `/system/copy-id`) and its containers (`/node/platform/container/...`). Permissions use `view.node.system`/`manage.node.system` and `view.node.platform.container`/`manage.node.platform.container`.
- **Domain-Specific Logic**: `features/cluster` may keep database-focused names such as cluster `Deploy`, because that feature turns Ivory cluster configuration into generic platform deployment requests.
- **Keeper Metadata**: `keeper.Metadata` is a separate interface from `keeper.Adapter`: Adapter covers operations against a running keeper, Metadata covers plugin self-description — `SupportedFeatures()`, `HasLeader()` and `DefaultTemplates()`. `HasLeader` states whether the engine elects a single primary **at all**, so a consumer can tell a missing leader from an engine that has none — clickhouse is the only plugin answering false. It is its own method because it cannot be inferred from `SupportedFeatures`: zookeeper declares neither switchover nor failover and still reports one. A leaderless engine reports its members as **`Replica`, never `Unknown`**: `Unknown` claims Ivory could not tell, and every consumer is entitled to treat it as a fault. **Metadata says nothing about what a deployment consumes, and there is no `keeper.Requirements`.** It used to declare `KeeperCredentials`/`KeeperUser` and `DbCredentials`/`DbUser`, and the plugin was the wrong owner of all four: what account a deployment ends up with is stated by the command that creates it — spilo names its superuser `postgres`, `CLICKHOUSE_USER` creates whatever the command says — so the *template* answers it (`keeper.DeploymentTemplateDefaults`), and a template the user wrote answers for itself instead of inheriting an engine-wide claim it contradicts. It named no ports for exactly the same reason; now it names nothing at all. Do not reintroduce it, in any shape: a plugin-level fact about a deployment is a fact about one particular deployment, wearing the wrong hat. The split lets plugins without a management API yet (plain postgres, `plugins/keeper/postgres`) still declare features and deployments. `database` and `tools` plugins keep `SupportedFeatures` on their Adapter for now.
- **One Plugin, One Registry**: a plugin family has exactly one registry, and a plugin is registered in it exactly once. `keeper.Plugin` and `platform.Plugin` are the interfaces it registers under — the operational interface(s) and `Metadata` embedded together, nothing else (`keeper.Plugin` embeds `Adapter` and `Metadata`; `platform.Plugin` embeds `System`, `Container` and `Metadata`) — so `plugins_context.go` can never register a plugin whose metadata half was forgotten, and there is no `KeeperMetadataRegistry`/`PlatformMetadataRegistry` to keep in step. The halves stay separate interfaces: **consumers depend on the narrow view they use**, declared as an unexported interface in the consuming feature (`node.keeperRegistry` resolves one plugin by key, `deployment.keeperRegistry` only ranges over `All()`, `deployment.platformRegistry` only asks whether a platform is registered) rather than on `*utils.Registry` itself, which is also what lets a test inject a fake that fills in one half and embeds the rest as a nil interface. The registry key type is `PluginType` in every family (`keeper.PluginType`, `database.PluginType`, `platform.PluginType`) — `Plugin` names the implementation, never the enum. `database` and `tools` have a single interface each (`Adapter`) and so register under it directly.
- **A Plugin Ships Its Own Deployments**: `keeper.Metadata.DefaultTemplates() []keeper.DeploymentTemplate` returns the ready-to-copy commands for that engine, one set per platform, and lives in `<engine>_metadata.go` beside `SupportedFeatures` — exactly the shape `database.Adapter.SystemRequests()` already uses for the query builder's shipped queries. It is on the interface on purpose: a new keeper plugin cannot be registered without answering it, so its deployments can never be forgotten in a catalog somewhere else. `features/deployment` only collects them from the registry (`Service.Defaults`) and never authors a command itself. **Each command is one whole `const`**, written with literal `{{placeholders}}` — never assembled from option/env/image fragments and never built by a helper that concatenates them. Two commands that differ only in a few flags are spelled out twice: they are data, and the whole point is that a reader sees the command the user will see. That duplication is deliberate; do not factor it back out. **Every shipped command also states its own `Defaults`** — node name, keeper port, database port — written as a literal `keeper.DeploymentCommandDefaults{...}` beside the command, never assembled by a helper, for the same reason the command is: a reader sees the values the deploy form will show. **Every shipped template states its own `Defaults` too** — `keeper.DeploymentTemplateDefaults{KeeperUser, DbUser}`, the accounts its commands create, which is what the deploy screen opens its credential sections on. Correctness is held by tests instead — each plugin's `_metadata_test.go` and the feature's `deployment_service_default_test.go` assert every placeholder is inside `keeper.Vars`, that every command names a node and both ports, that node names are unique within a template, that a single-host template's three nodes share no port, and that a template whose commands reference `{{dbUser}}`/`{{dbPass}}` names the database user it creates — otherwise the deploy screen would open that pair switched off and the deploy would die on a placeholder nothing filled in.
- **The Verb Belongs to Ivory, the Options Belong to the User**: every `Container` method writes its own `docker <verb>` — `docker ps -a`, `docker rm`, `docker logs`, and `UpContainer`'s `docker run`. The command text a user writes supplies **options only**. `UpContainer` deploys a container and nothing else, so taking the executable from the command text would make it a remote shell that happens to be named `UpContainer`; `normalizeRun` therefore prepends `docker run` and drops the user's own `docker`/`run` rather than duplicating it, since a command is usually copied in whole. It drops **nothing else** — not a `sudo`, not any other prefix: **how Ivory reaches docker on a host is the connection's business, not one command's**, and a deploy able to ask for root while `stop`, `rm` and `logs` cannot is a half-answer either way. Eating the prefix was worse than ignoring it, which is what the old `trimDockerPrefix` did — it swallowed the `sudo` and put only `docker` back, so a command needing root ran without it and said nothing. sudo belongs on the connection, where every method can reach it; until it lives there, a command that names it simply fails visibly.

  `UpContainer` is the only method that normalizes anything, and not because it is special — because it is the only one whose user-supplied text could restate the verb. Every other method takes a *value* (a name, a path, a tail count) and writes its command in full, so there is nothing to drop. `ExecContainer` also takes command text, but that text runs **inside** the container, where the executable is genuinely the user's to choose (`etcdctl`, `mongosh`, `psql`) — its verb, `docker exec -- <name>`, is already Ivory's, and a leading `docker` in a post script must **not** be stripped, since inside a container that is docker-in-docker and a legitimate thing to run.
- **Ivory Does Not Generate Deployment Commands**: a deployment is a command the *user* writes, saved as a template (see `features/deployment`). There is no `keeper.DeploymentSpec`, no `platform.DeploySpec` and no `RenderOptions`: nothing renders a command from structured plugin data, so keeper plugins and platform adapters stay mutually ignorant without an n×m matrix in between. `platform.Container.UpContainer(connection, command)` runs the already-interpolated command verbatim — it does not inject a name, an image or a startup command, since what runs must be what the user read on screen.
- **The Interpolation Vocabulary Is Closed, Typed, and Small**: `keeper.Vars` is the complete, hard-coded list of `{{variables}}` a command may use, and it is deliberately *only* what Ivory itself needs to register and reach the cluster afterwards — the node's own identity and endpoints (`{{cluster}}` `{{name}}` `{{host}}` `{{sshPort}}` `{{keeperPort}}` `{{dbPort}}`, i.e. `NodeConfig`) plus the two credential pairs resolved from their own vaults (`{{keeperUser}}` `{{keeperPass}}` from the keeper vault, `{{dbUser}}` `{{dbPass}}` from the database one — separate variables because they are separate answers, even where one engine answers both endpoints). **Everything else is literal text in the command**: a peer port, a member list, a coordinator address, which node is the leader — these are values only the operator knows, and they read better as the plain text they are than as a variable plus a form field somewhere else. Do not add a variable for one engine's needs. A placeholder outside `keeper.Vars` is a validation error on template save and on deploy, never a new variable. `keeper.Interpolate(text, keeper.Values)` takes a struct, not a map, so no caller can invent a key; adding a variable means adding a `Var`, a `Values` field, and a `DeployVarOptions` entry on the frontend (`{[key in DeployVar]: DeployVarMeta}`, a mapped type, so a missing entry fails `npm run build`), and `keeper_metadata_test.go` asserts the `Var` ↔ field mapping stays exhaustive both ways. Values are scoped **per command**: everything a command can reference belongs to that one deployment, so one node's values can never reach another node's command.
- **The Threat Model: Protect the Execution, Not the User From Themselves**: a deployment *is* arbitrary command execution on a host the user chose, by a user who holds `manage.node.platform.container` or `manage.cluster.create`. That is the product, not a hole in it. So when judging anything here, ask **only** whether what runs is what the user read on screen. If they can see the whole command and they typed the inputs themselves, a command that wipes the host is their decision and their responsibility — with that much power, that much responsibility — and it is not a finding, however alarming the command looks. Do not add validation, allow-lists or "dangerous command" checks to save them from a command they wrote and can read. What *is* ours to guarantee: (1) **fidelity** — the command that executes is character-for-character the one shown, so a value Ivory substitutes can never add an argument, close a quote, or become syntax the reader did not see; (2) **confidentiality** — a secret Ivory holds does not leak into somewhere the user never looked (a job id, a log file, an error message); (3) **honesty** — where what runs is *not* what is shown, say so on screen, which is the whole job of `DeploymentPreviewNote` and the password mask. A bug here is a bug when it makes the running command differ from the read one. It is not a bug because a user could write something harmful.

  The same line holds for ordinary mistakes, not just dangerous ones: **do not build guards against operator error the operator can already see.** Two templates defaulting to the same port on one VM, a host that is not reachable, a member list naming nodes that were called something else — those are the operator's to check, and adding validation for them buys nothing but a rule to fight later. What is worth fixing is a mistake Ivory *hides*: a value silently dropped, a placeholder that reaches the shell as literal text, a failure reported as success, an error that names the wrong cause. Make the problem legible, then get out of the way.

  Deliberate scaffolding is not a finding either. `backup_service.go`'s `switch latestBackupVersion` has an unreachable `default` because there is one version today — it is the branch the next one will use, and reporting it as dead code just asks the author to defend the plan. The same goes for a type or a route declared ahead of the screen that will call it. Ask whether the code is waiting for something known to be coming; if it is, leave it alone.
- **Split, Then Interpolate, Then Hand the Platform a Finished Command**: the three layers stay strictly separated. `plugins/platform` knows connections, arguments and containers, and **must never know what a `{{placeholder}}` is** — `Container.UpContainer(connection, command []string)` and `ExecContainer(..., command []string)` take the exact arguments that will run, already filled in. `plugins/keeper` owns the interpolation vocabulary (`Var`, `Values`, `Interpolate`) and knows nothing of docker, ssh or tokenizing. `features/node` is the composition point and the only place the two meet: `resolveCommand` calls `platform.SplitCommand` first, fills each already-separated argument in with `keeper.Interpolate`, and passes the result down. Do not push interpolation into the adapter — not as a template plus a callback, not as a values map, not in any form; that inverts the dependency and was reverted once already. The order is what makes escaping unnecessary: a value put into an argument that is already separated cannot introduce an argument boundary, close a span the template author opened, or be re-read as syntax, so a password holding `'`, `"`, `\`, a space, `$` or a backtick simply works. This replaced an escaper (`escapeInterpolatedValue` + a `platform.ValueEscape` marker) that had to guess how many parses a value would face; **no new escaping mechanism should be added** — if a value looks like it needs escaping, it is being substituted in the wrong place. `SplitCommand` lives in `platform` because it defines how command text becomes the argument list that boundary speaks in. The one thing this cannot reach is a shell the command *itself* starts: where an argument is `sh -c '...'`, the container parses that script a second time, so such a script reads what it needs from env its own command sets (postgres reads the `$POSTGRES_PASSWORD` its own `docker run` states) rather than naming `{{dbPass}}`. `TestDefaultsKeepCredentialsOutOfNestedScripts` holds exactly that line and nothing wider. `console.Command.Id()` hashes for the confidentiality half: an id is persisted as a log file name and broadcast as a job line.
- **A Post Script Is a List of Commands, Never a Script**: `DeploymentCommand.PostScripts []string` runs its steps in order, each as its own `ExecContainer`. It is a list because **nothing may assume a shell**: the images these run in are increasingly distroless — `quay.io/coreos/etcd` holds only `etcd`, `etcdctl` and `etcdutl`, and `registry.k8s.io/etcd` dropped `/bin/sh` at 3.6.5 — so there is nothing to interpret an `&&`, and a `sh -c '...'` post script silently never ran. One command per step is also what lets a step name `{{dbUser}}`/`{{dbPass}}` directly: with no shell, each argument is filled in after the split and nothing parses the value. Chasing an image that still ships a shell is the wrong fix and dates immediately, exactly as `bitnami/redis` did. In the template editor this is one field, one command per line.

- **Node Executes One Node; Cluster Only Batches Them**: `features/node` owns keeper-deploy execution in `node_service_keeper_deploy.go` — `KeeperDeployUp` (run one node's command), `KeeperPostDeploy` (run its post-script), `KeeperDeploy` (both, the self-contained single-node action), and `getValues` (build one command's scope from its own request alone). There is **no deploy spec**: the forms take everything they used to ask the plugin for from the template they are running. There is **no deploy plan**: previewing a command is a regex substitution the frontend does locally, and the backend stays authoritative because `PlatformContainerUp` hard-errors on any unresolved placeholder. The route is `POST /node/platform/container/keeper/deploy`, guarded by `manage.node.platform.container`. The one thing `KeeperDeploy` still asks the registry is whether the plugin exists at all (`ValidateKeeperPlugin`), which `cluster.Deploy` asks too before it stores a cluster naming it. `node` defines **no node struct of its own**: `KeeperDeployRequest` is flat, and host/ssh port come from the `PlatformVaultConnection` it already carries. `cluster.Service.Deploy` (`POST /cluster/deploy`) validates, creates/reuses vaults, writes the cluster record, then loops `KeeperDeployUp` per node and runs post-scripts in node order — a script needing the whole cluster up (etcd's auth enable, mongo's `rs.initiate`) therefore belongs on the *last* node. **The frontend calls exactly two deploy actions**: `useRouterClusterDeploy` (whole cluster) and `useRouterNodeKeeperDeploy` (single node), and whichever endpoint a dialog calls is the feature it lives in — `ClusterDeploy.tsx` in `features/cluster`, `ContainerKeeperDeploy.tsx` in `features/node`. **The single-node screen fills nothing in**: the node is the one the dialog was opened on and its ports are the ones the chosen command states, so every field on it is disabled — a cluster is where a node's identity is chosen, not a container. **Its one choice is which of the template's nodes runs here**, a toggle above the node card that starts on the first and is hidden for a one-node template: a template describes a whole cluster, and only the operator knows which of its members this host is meant to be. Both take their template UI from `features/deployment`. **There is one deploy dialog, not two**: `DeploymentTemplateDialog` is the router over the `Step` union (`list` | `create` | `update` | `deploy`) and owns which screen is up and the title bar's back arrow — three of its four screens (`DeploymentTemplateList`, `DeploymentTemplateForm` twice) are the same wherever it is opened, so a caller supplies only the fourth, through `renderDeploy(DeployScreenProps)`. `ClusterDeploy`/`ContainerKeeperDeploy` are now just that call plus a trigger: the dialog's title and icon, its `ManageAccess` gate where there is one, and which form runs the template. Screens take props in and call a callback out; none of them knows about another, and the navigation graph is written once, in the router. **The dialog fetches nothing before it mounts a deploy screen**: a deploy form seeds its `useState` from the template it was handed — the credential usernames, the per-node ports — and the template is already in the `Step`, so there is nothing left to wait for. The "a router only mounts a screen once what it needs has loaded" rule is satisfied by construction rather than by a query gate. What a deploy leaves behind is not a deployment screen at all — its logs are `shared/component/box/DialogLogsScreen`, which takes `string[]` and knows nothing about deployments; the pixel height it fixes is the dialog's geometry, not a deploy's. A `*DeployResponse` per feature was two copies of that. **The response is rendered from inside the deploy form**, not next to it in the router, so backing out of the logs of a deploy that failed on its third node returns to the form still filled in — the router still owns the transition, by carrying `logs` on the `deploy` step. **A deploy sends one answer per credential, never two**: `cluster.Deploy` rejects a vault id alongside an inline username/password (`ErrSshCredentialsAmbiguous`/`ErrDatabaseCredentialsAmbiguous`), so the form omits whichever mode is not selected and clears the other's vault id when switching. **The typed ssh password exists to install the generated key, and for nothing else**: when no ssh vault is picked, `Deploy` generates a keypair, and a generated key authenticates nothing until its public half is in the host's `authorized_keys` — so `Service.authorizeSshKey` runs `nodeService.PlatformSystemCopyId` against each host (`Service.sshTargets`, one entry per host+ssh port, since a single-host cluster's three nodes share a VM) before any node starts. Every connection after that is by key, out of the vault. It runs only in the generated case: a vault the user picked holds a key they already authorized, and the ambiguity check means there is no password to install it with anyway. A failure aborts, like the rest of the preparation phase — nothing has been started on any host yet, so there is nothing left to troubleshoot, and every node would otherwise fail with the same auth error one at a time. The vault manager's own "copy" is `navigator.clipboard.writeText` (`VaultListItem.handleCopy`): it puts the public key on the user's clipboard to paste by hand, and installs nothing. **Create the cluster first, then deploy. This is settled — never treat it as a bug and never reorder it.** `cluster.Deploy` writes the cluster record, with *every* configured node and its vaults, **before** it starts a single container, and keeps all of them whether or not they came up. Nothing is rolled back once that record exists: not the cluster, not a node whose container failed, not the vaults, and never the container itself. **A failed `docker run` leaves its container on the host on purpose.** That container is the only evidence of what went wrong — it may have been created and exited, or started and crashed on its own config — and its logs, its exit code and an exec into it are the only things that say why. Ivory reaches it through the cluster's own node config and ssh vault, so a deploy that registered nothing, or registered only the nodes that succeeded, hides exactly the failures the operator opened Ivory to look at and leaves them ssh-ing into the host by hand. Every reordering of this looks like an improvement — no cluster of nonexistent nodes, no orphan vaults, a tidy list — and every one of them buys that tidiness by throwing away the ability to troubleshoot a deploy that failed, which is the more valuable of the two. A partial deploy says so in its logs instead. The only thing `rollbackVaults` still covers is the paths that fail *before* the record exists (a vault create, the `Update` itself), where nothing points at those vaults and no retry could ever find them again. Template names are unique **within one keeper/platform pair** and trimmed before storing, because that pair is the list the user picked the name in.
- **Node Name vs Host**: `NodeConfig.Name` is the node's own name, unique within the cluster and independent of its host — it is the deployment's identity (`{{name}}`, `--name`) and the name the platform addresses the container by, which is why `Container`/`ContainerOverview` take it as a prop instead of reusing `connection.host`. `Host` stays the *connection* identity, because `cluster_service_discovery.go` matches keeper-reported `host:keeperPort` against it. **The name is mandatory on every write**: `Service.validateNodeNames` (in `cluster_service_crud.go`, shared by `Update` and `Deploy`) rejects an empty or duplicated one, and the frontend `NodeConfig.name` is a required field. Where a name comes from, in order: what the keeper itself calls the member (`keeper.Response.DiscoveredName` → `mapKeeperResponse`, so `Detect`/`Fix`/an unconfigured node found in a keeper response are named the way patroni or etcd names them), what the user typed (the deploy form, or the node block's `Name` field in `NodeHeadForm`), otherwise the host. That last fallback is applied in three places for the same reason — `mapKeeperResponse` for a keeper with no member names of its own, `getNodeConfig` for the cluster list's `host:ports` rows, and `Response.withNodeNames` in the repository for clusters stored before names existed. The cluster list edits hosts and ports only, so `ListRow.getEditedNodes` carries each row's existing name over rather than resetting it to the host.
- **A Deploy States Every Port**: keeper, database and ssh ports are all mandatory at deploy time, and none of them is derived from another. They are stated by the template's command (keeper and database) or typed by the user (ssh, and either of the others the command leaves out) — **never taken from the keeper plugin**, which is why the plugin is not asked about a deployment at all any more. `ClusterDetect` asks for its port outright for the same reason: the port a running keeper answers on is something only the operator knows. `cluster.Deploy` rejects a node missing any port (`ErrClusterNodePortsNotProvided`) and `node.KeeperDeployUp` rejects it again (`ErrKeeperDeployPortsRequired`). There is no ssh-22 fallback, no `keeperPort ?? dbPort`, no `withKeeperPort` form mode and no `NodeInputFormat` mirroring one port into another: a node domain string is always `host:keeperPort:dbPort:sshPort` and every segment it omits stays missing. Typing a port that used to fill itself in is the deliberate cost of that.
- **The Keeper's Credentials Are the Keeper's Own**: a deploy asks for keeper credentials and database credentials separately — a `Keeper Credentials` and a `Database Credentials` section on the form, `{{keeperUser}}`/`{{keeperPass}}` resolved from the keeper vault beside `{{dbUser}}`/`{{dbPass}}` from the database one, and a `KeeperId` beside `DatabaseId` in `node.Vaults`. An engine whose keeper endpoint *is* its database (etcd, redis, clickhouse, plain postgres) has its templates name both usernames, and is asked twice; **pointing both at the same vault entry is the user's answer to give**, and getting them to match is their responsibility. Ivory never links one vault to the other on their behalf — the old `SharedCredentials` flag that silently wrote the database vault id into `Vaults.KeeperId` was a bug, not a convenience. **Whether a deployment has either pair at all is the user's answer, not the engine's.** `ClusterDeployCredentials` offers three modes — `VAULT`, `NEW` and `NONE` — and `NONE` is offered on keeper and database but never on ssh, which is how Ivory reaches the host in the first place. So the server no longer asks a plugin what a deploy needs: it writes a keeper vault because a keeper password was typed, a database vault because a database password was typed, and nothing otherwise. What is left to validate is only that an answer is whole (`ErrKeeperCredentialsIncomplete`/`ErrDatabaseCredentialsIncomplete` — half a pair would be stored as a vault entry that authenticates nothing) and that it is single (`ErrKeeperCredentialsAmbiguous`/`ErrDatabaseCredentialsAmbiguous` — a vault and an inline pair are two answers to one question). **No username is locked**: `ValidateKeeperLockedCredentials` and `resolveLockedUsername` are gone, a template's `Defaults` seeds the username field as a suggestion the user may replace, and the vault dropdown is no longer filtered to entries carrying it. A username the engine did not suggest is stored as typed — the command that creates the account is theirs to edit, so a mismatch is theirs to make. `ClusterDeployCredentials` is that one section, rendered three times (ssh, keeper, database), so the three answers cannot drift apart in shape.
- **No `singleHost` Flag**: several nodes on one VM is a *template*, not a mode. The shipped `<Keeper> (Single Host)` template uses `--network host`, publishes no ports, mounts no volume, writes a distinct peer port into each command and states each node's own client port in that command's `Defaults` — which is exactly what the deleted flag used to compute, now as readable text. Two consequences of host networking are wrong in every command that forgets them: docker **rejects `--hostname` outright** alongside `--network host`, so a single-host command never sets it; and host networking joins no docker network, so there is **no embedded dns** — a member list, a leader address or a replica list addresses peers by `{{host}}`, never by container name. The port a peer answers on is literal text beside it (`{{host}}:2380`, `host={{host}} port=5432`), because it is another node's port, not this one's. Where the image fixes a port that three copies cannot share, the command states it rather than the template being declared undeployable: clickhouse writes `<tcp_port>{{dbPort}}</tcp_port>` into the `config.d` file it was already generating, and zookeeper overrides the entrypoint's hardcoded `clientPort` through `ZOO_CFG_EXTRA` (java properties, later key wins) and switches off the admin server it cannot move.
- **Deployment Templates**: `features/deployment` owns them — a `Template` is an ordered list of `TemplateCommand`s, one per node, plus the keeper and platform it targets and a `TemplateDefaults` of the credential usernames its commands create, and nothing about *where* they run (the host is supplied at deploy time only). It sits under both deploy dialogs: it imports `KeeperPlugin`/`PlatformPlugin`/`DeployVar` from `node`, and `cluster`/`node`/`core` import its screens back — the shared halves of a deploy screen live here (`DeploymentTemplateDialog`, `DeploymentCommandPreview`, `DeploymentLogs`, `DeploymentPreviewNote`, `useDeployVaultCredentials`, `DeployCredentials`) precisely so neither of the two features owns a copy of the other's. It borrows `query`'s `system`/`manual` vocabulary (`deployment.CreationType`) but not its storage: the system templates are **not seeded into the bucket** — `Defaults()` computes them from the keeper plugins on every request, so they carry a synthetic `default:<platform>:<name>` id, can never be edited or deleted, and always track the current version. The repository stores manual templates only. **The UI flow is: choose a template and run it; when none fits, write a new one or copy and adjust an existing one, then run that.** **Every template runs the same way, system or not** — picking a row goes straight to the deploy form. A system template is restricted only in that it cannot be edited or deleted (it is computed, not stored, so that holds by construction); it is copied, not walled off. The row's buttons are the other two things you can do with one: edit your own, or copy any of them into one you own. `DeploymentTemplateForm` covers all three ways a template comes to exist (new from scratch, copy, edit) and always returns to the list on save, so a template you just wrote is picked the same way as any other rather than being special-cased into the deploy form. The three are two props rather than three components: `edit={false}` with an optional `source` (new or copy — the same POST, and a source only seeds the editor) and `edit={true}` with a required `template` (the only one that needs an id to write back to), a discriminated union so `{edit: true}` without a template cannot be written. Its Create/Save button lives in the form's own `DialogScreen`, which is what keeps it pinned in the same place as `Deploy` instead of trailing off the bottom of a long form. **A command carries what only it can know; the deploy supplies the machine.** A `TemplateCommand` is the command text, its post script, and a `Defaults` of node name, keeper port and database port — `keeper.DeploymentCommandDefaults`, aliased into the feature as `deployment.CommandDefaults` exactly as `TemplateCommand` aliases `DeploymentCommand`, so `backup` never imports a plugin package. Those three are on the *command* because a command and the endpoints it answers on are one fact: a single-host template writes a distinct peer port into each of its commands, and only that command knows which client port has to match it — one engine-wide pair cannot say that, and a form that seeded every card from such a pair put three nodes on one port and could not deploy. The name is there for the same reason: a member list naming `etcd2` is only correct if the node running that command is called `etcd2`, a coupling that used to hold by accident because a *frontend display-name constant* happened to generate matching names. **Credentials are the other way round: they belong to the template, never to a command.** `deployment.TemplateDefaults` (`keeper.DeploymentTemplateDefaults`) holds `KeeperUser` and `DbUser` and nothing else — one cluster authenticates one way, so three commands each naming their own username could only ever disagree, and it is the same reason ports are per-command and these are not. A username there means the deployment ends up with that account (spilo's `postgres`, etcd's `root`), so the deploy screen opens that credential on `VAULT` with the name filled in; a template naming none opens it on `NONE`, which is what replaced a hidden section. **A password is never in a template** — a template is stored, read and copied, and a secret in one would be a secret in all three. In the editor the two sit in matching boxes: a template-level `Cluster Defaults` beside `Variables`, and a `Node Defaults` inside each node's command. **Host and ssh port are deliberately in neither** — both describe the machine being deployed onto, which is the one thing a template never knows. **A port comes from the template or from the user, never from a fallback**: a command that states none leaves the field empty and red on Deploy, because the alternative — borrowing the engine's single default — is exactly what put three single-host nodes on one port. So `ClusterDeployForm.getInitialNodes` seeds each card from its own command and nothing else (ssh port included: it starts empty, there is no 22), and `ContainerKeeperDeployForm`, whose fields are all read-only, disables Deploy outright when the chosen command names no ports — the template is where that is fixed. Ports are range-checked on save (`ErrTemplatePortInvalid`) and the default node name is trimmed like the template's own. Node names are written without a separator — `etcd1`, `postgres2` — in `Defaults`, in every literal member list that references them, and in the frontend fallback. `ClusterDetect` asks for its one port outright rather than seeding it from the plugin, and its effect only carries a keeper/database change from the list filter behind it into a dialog mounted before that change. The command text itself is edited in the template and is **read-only on the deploy screen**, where it is shown already interpolated (`interpolateCommand`) so the user reads exactly what will run — the vault credentials stay as placeholders, since they never leave the server. `DeployVarOptions` carries each variable's `label`, `example`, `secret` flag and `scope` — a mapped type, so a new variable cannot be added without all four. The template editor's `Variables` box pairs every token with its `example` in a two-up table, above one line saying the deploy screen is what fills them in: a reader opening a template has no reason to guess that on their own, and an example says more than a description at the cost of a column instead of a line. **The list is grouped by `DeployVarScope`, not flat** — `Node` (`{{name}}` `{{host}}` `{{sshPort}}` `{{keeperPort}}` `{{dbPort}}`) against `Cluster` (`{{cluster}}` and both credential pairs) — because that is the one thing a template author has to know before writing a command: `{{name}}` is a different value in every node's command, `{{dbPass}}` is the same one in all of them. The two groups are named after how many values a variable has in one deployment, and they are deliberately the same split as the editor's two `Defaults` sections, so a reader learns it once. **A preview fills in `{{keeperUser}}`/`{{dbUser}}` but never their passwords** — the form already knows the username (typed into the NEW fields, or read off the chosen vault entry, which is why `useDeployVaultCredentials` shares `OptionsVault`'s vault query) so showing it makes the preview read like the real command, while the password is rendered as `DeployPasswordMask` and only ever substituted for real by `node_service_platform.go`'s `getExecutionValues`, which decrypts it out of the vault at execution and escapes it. That mask is the one thing `DeploymentPreviewNote` explains, because it is the only place where what is on screen is not what runs. Never describe either as coming "from the vault" on screen: the form supplies credentials two ways — an existing vault entry, or new ones that `cluster.Deploy` writes to a vault before any node starts — so only one of them looks like a vault to the user. **A template's command count is its node count** — `ClusterDeployForm` renders exactly that many node cards (`ClusterDeployNode`, one per command) and nodes are never added or removed at deploy time. A node card is a plain framed `Box` with no heading at all, unlike the `TitledBox` sections it sits under: there are several of them, read in order, and their fields name themselves — a title numbering each card only repeated what the layout already said (the template editor's node is a collapsible `SubContentBox` instead, since there a node is a command you fold away) — only the read-only command folds away, with its post script beside it so a template that changes something after boot (etcd's `auth enable`) is visible before you run it — that fold is `DeploymentCommandPreview`, one component for both screens, differing only in `defaultOpen`: the cluster form folds it because there is a form around it, the single-node screen opens it because there is nothing else on it to read. A cluster of a different size is a different template, edited in `DeploymentTemplateEditor`. That is why the deploy dialog has no free-form node list any more. **The deploy form reports errors on the field, not in a list** — every rule `cluster.Deploy` rejects (cluster name, per-node name and host, **all three of a node's ports**, ssh credentials always, keeper and database ones unless the user switched that pair to `NONE`) marks its own input red on Deploy, so there is no `WarningList` restating what a red border already says; the one exception is a duplicate node name, which is shown live as `helperText` because a border alone cannot explain it. **`ClusterDetect` is the same form for a cluster that already runs**: the same `TitledBox island` sections, the same `FieldRow`, the same click-Detect-to-see-the-errors rule, and the shared `ClusterOptionsBox` (the `Cluster Options` `SubContentBox` with the plugin selectors disabled) that `ClusterDeployForm` folds its options into. It asks for one node instead of a card per command, and that node gets a heading where a deploy node card does not — there is exactly one of it, so the frame has to say what it is.
- **Request Naming**: Use neutral platform request/response names at the node/platform boundary, such as `PlatformUpRequest`, `PlatformLogsRequest`, `PlatformVaultConnection`, and `PlatformResponse`. Request fields like `name` should identify the target deployment generically; adapters map that to a Docker container name, Kubernetes resource name, pod name, etc.

## Adding a New Keeper or Database Plugin
A new database engine is added as a keeper plugin, a database plugin, or both — never by baking engine-specific logic into `features/`. `plugins/keeper/redis`, `plugins/keeper/clickhouse`, `plugins/keeper/zookeeper`, `plugins/database/redis`, `plugins/database/clickhouse`, and `plugins/database/zookeeper` are reference implementations, built exactly to this checklist; `plugins/keeper/postgres` (minimal, direct-protocol keeper) and `plugins/database/etcd` (console-command adapter) are the smallest templates to copy from, `plugins/database/postgres` (full SQL adapter, split by concern) the largest.

**Backend, in order**:
1. **Client wrapper** (`server/clients/<engine>/<engine>_client.go`) — only if the engine needs its own driver; skip this if an existing client already talks to it (both etcd plugins reuse `clients/etcd`). Give it a `Config` struct, a `Connect(ctx, Config) (*Client, string, error)` that validates host/port and eagerly pings so a bad connection fails at connect time instead of on the first real command, and a `Close`. One client package per engine, shared by that engine's keeper and database plugins — never a generic multi-engine client. An engine that genuinely speaks two unrelated protocols keeps both in that same package rather than splitting into two client packages: `clients/zookeeper` has both `FourLetterCommand` (the plain-text admin protocol `plugins/keeper/zookeeper` uses for health/config) and `Connect`/`Close` (the real znode wire protocol `plugins/database/zookeeper` uses for data operations) side by side.
2. **Keeper plugin** (`server/plugins/keeper/<engine>/`), if the engine has an HA story worth exposing: `List` must report `DiscoveredName` when the engine has a real member name of its own (patroni's member name, etcd's member name) — that is what becomes `NodeConfig.Name` on auto-creation; an engine that identifies members by `host:port` (mongo, redis, clickhouse, zookeeper, native postgres) leaves it nil so the node falls back to its host, rather than reporting an endpoint as a name. Implement the full `keeper.Adapter` interface (all 12 methods) — an operation the engine genuinely can't do returns `keeper.ErrNotSupported` with `http.StatusNotImplemented`, it is never omitted from the interface. Implement `keeper.Metadata` (`SupportedFeatures()` + `HasLeader()` + `DefaultTemplates()`) declaring only what `Adapter` really supports. It asks nothing about credentials: what account a deployment ends up with is stated by the template that creates it, not by the engine.
   - **Implement `DefaultTemplates()` in the same file**, returning one multi-host and one single-host template of three commands each, hand-written for `platform.Docker`. This is compile-enforced by `keeper.Metadata`, so the plugin cannot be registered without it. Use only variables from `keeper.Vars` — the plugin's own `_metadata_test.go` and `deployment_service_default_test.go` both fail otherwise. Give every command a `Defaults` naming its node (`<engine>1`, `<engine>2`, …) and both ports; in the single-host template those ports must all differ, since the three nodes share one port namespace. Give every *template* a `Defaults` naming the accounts its commands create — the keeper user, the database user, or neither: an engine that is its own keeper (etcd's `root`, redis' `default`) names both, patroni names only the database one because the shipped spilo deployment leaves its rest api unauthenticated, and zookeeper and mongo name neither, which is how the deploy screen knows to open those sections on `NONE`. A template whose commands reference `{{dbUser}}`/`{{dbPass}}` **must** name a database user, or it cannot deploy.
   - **A leader/replica asymmetry is just a different command at index 0.** Postgres's replicas rebase with `pg_basebackup` and redis's set `REDIS_REPLICATION_MODE=slave`, so their templates carry a plain command first and a bootstrap command for the rest — there is no `EntryScriptReplicasOnly` flag any more. If the official image can't be configured through env vars alone (redis's only takes port/password as CLI flags), pick one that can — the redis templates use `bitnami/redis` for exactly this reason.
   - **The entry script is the tail of the command**, after the image, not a separate field. `docker` tokenizes quote-aware, so a multi-line `sh -c '...'` stays one argument with its newlines intact while the whitespace between flags collapses.
   - **Write a complete, working command.** A coordinator address, a member list, a peer port, the leader's host — all of it goes in as literal text with real values (`etcd-1=http://etcd-1:2380,...`, `ETCD3_HOSTS="etcd-1:2379,..."`, `-p 2380:2380`), so a copied template deploys as-is once the hosts are filled in. Say in the description which names it assumes ("Name the nodes etcd-1..3 or edit the member list to match"). Never reach for a new variable to avoid a literal.
   - **A post-script** is a single opaque script exec'd into the container after the batch is up. It belongs on the command that should run it — the last one when it needs the whole cluster (etcd's auth enable, mongo's `rs.initiate`). A plugin needing several steps chains them itself with `&&`.
3. **Database plugin** (`server/plugins/database/<engine>/`), if the engine is queryable - and even if it's "only" an infrastructure coordinator with no real query use case, as long as it's reachable through `KeeperPlugin`'s dbPlugin pairing (see Frontend step 1): implement `database.Adapter` (`QueryExecutor`/`SchemaInquirer`/`SessionManager`/`MetadataProvider`). Split files by concern the way `postgres` does (`_query.go`/`_schema.go`/`_session.go`/`_metadata.go`) once the adapter has enough surface area; a small adapter (etcd, redis, zookeeper) can keep everything in fewer files. For a SQL-ish engine follow the `postgres` template: real `GetMany`/`GetOne`/`GetFields` and real schema introspection (see `plugins/database/clickhouse`). For a non-SQL engine follow the `etcd` template: a generic console-command executor is fine (see `plugins/database/redis`'s `GetFields`, which tokenizes and passes straight through to the engine's own `Do`-style command call rather than hand-parsing a fixed verb set; `plugins/database/zookeeper` hand-parses a small fixed verb set instead - `ls`/`get`/`create`/`set`/`delete`/`exists` over znode paths - since its client library has no single generic passthrough call the way redis's `Do` does). Don't force an operation to "work" when the engine has nothing correct to map it to — return `ErrNotSupported` instead (see `clickhouse_adapter_session.go`'s doc: ClickHouse's `SessionManager` is fully unsupported despite being SQL-based, because it identifies a running query by a string `query_id`, not the int pid this interface's `Cancel`/`Terminate` require; `plugins/database/zookeeper`'s `SchemaInquirer`/`SessionManager` are unsupported outright for the same reason etcd's are - no db/schema/table hierarchy and no per-query session/pid concept).
4. **Register the plugin**: add a `PluginType` const to `keeper/keeper_model.go` and/or `database/database_model.go`, then instantiate the adapter and register it once — as `keeper.Plugin`, which requires both halves — in `plugins/plugins_context.go`, following the existing import-aliasing convention (`pgkeeper`/`etcddb`-style) whenever the new package name collides with another import in that file.
5. **Tests**: every new file gets a `_test.go` counterpart, table-driven, matching the file it tests (see Testing Guidelines). Keep mapping/parsing functions (`mapNode`, `parseInfo`, `parseQuery`, ...) pure so they're testable without a live connection; guard clauses (`ErrNotSupported`, `ErrCredentialsRequired`, host/port validation) are tested directly against the adapter, not mocked out.

**Frontend, in order** (the first two are compiler-enforced, the third is not):
1. Add the new value to `KeeperPlugin` (`features/node/api/NodeType.ts`) and/or `DbPlugin` (`features/query/api/QueryType.ts`). **Every `KeeperPlugin` must pair with a `DbPlugin`** - `KeeperPluginOptions[keeper].dbPlugin` is genuinely consumed (`List.tsx`/`ListEmptyInfo.tsx`/`ListRowNew.tsx` use it to auto-select the database plugin when creating a new cluster), so a keeper-only engine with no real query interface (`plugins/keeper/zookeeper`) still needs a real, matching `database.Plugin` (`plugins/database/zookeeper`) to pair with - reusing an unrelated existing `DbPlugin` would be actively wrong (the query console would speak the wrong wire protocol entirely).
2. Add a matching entry to `KeeperPluginOptions`/`DbPluginOptions` in `shared/helper/HelperUtils.tsx` — these are `{ [key in Plugin]: ... }` mapped types, so a missing entry fails `npm run build`, not just lint.
3. Add a selector item in `core/widgets/options/OptionsPlugins.tsx` (`renderKeeperItem(...)` / a plain `<MenuItem>`) — this is a manual list, not compiler-checked, so it's easy to forget; skipping it leaves the new plugin silently unselectable in the UI even though everything else compiles.
4. Run the Mandatory Check (`cd app && npm run lint && npm run build`) plus any affected `npm test`.

**Docs**: add a row to the "Supported Keepers" table in `README.md` (Keeper / Database / Stage / Why) — new plugins normally start at `ALPHA`.

## Nomenclature
- **Node**: Refers to a single server entity (Hardware + Software).
- **Keeper**: Refers to the HA management tool (e.g., Patroni).
- **VM**: Refers specifically to the virtual machine/host level.
- **Platform**: Refers to the deployment/troubleshooting target that Ivory integrates with, such as on-prem Docker-over-SSH now and Kubernetes/OpenShift in the future.
- **Deployment**: Refers to the generic platform-managed thing Ivory deploys, stops, deletes, lists, or reads logs from. Avoid using `Container`, `Pod`, or `DatabaseRegistry` for generic platform APIs.
- **Job**: Refers to a generic command execution entity managed by a background goroutine, supporting event-driven status updates, console logs persistence, and live streaming.

## Coding & UI Standards
- **Comments**: Default to no comments. Only write one when the WHY is non-obvious — a hidden constraint, a subtle invariant, or behavior that would surprise a reader; never to restate what a well-named identifier already says. Exported Go functions/methods, interfaces, and model/struct types may get a single concise line documenting a non-obvious behavioral contract (e.g. "AuthContextMiddleware is like ValidateMiddleware but never aborts"), but never a multi-line block. Unexported helpers get no comment unless the WHY test above applies.
- **Go Import Aliases**: Do not alias imports unless the name actually conflicts. An import of a package with the same name as the enclosing package is NOT a conflict (e.g. `plugins/database/postgres` imports `ivory/clients/postgres` plainly and references `postgres.Connect`). Aliases are justified only when: (1) two imports in the same file share a package name (e.g. `pgkeeper`/`etcddb` in `plugins/plugins_context.go`; or `coreConfig "ivory/core/config"` in files that also import `ivory/features/config` — both packages are named `config`), (2) the import name collides with a local identifier, or (3) the plain name would be genuinely misleading next to same-named local types (`nethttp` inside `clients/http`). Spelling out a package's real declared name when it differs from the path's last element (`clientv3 "go.etcd.io/etcd/client/v3"`) is not an alias and should be kept.
- **Surgical Renaming**: When asked to rename components or fields, ONLY update the terminology. DO NOT refactor implementation logic, move methods to props, or change the component structure unless explicitly directed.
- **Data Synchronization**: When syncing frontend types with backend changes, perform the MINIMAL necessary updates to ensure compilation. DO NOT redesign or refactor UI components during a data sync task. If a type change appears to require a major UI redesign, ASK for clarification first.
- **A Dialog Is a Router Over Screens**: `DialogButton` is the shell only — trigger, title, close, back arrow — and renders no action bar of its own. A screen supplies both of its halves through `DialogScreen`: the scrolling content, and an action bar that is a **sibling** of the scroll container rather than its last child, which is what pins the buttons to the bottom of the dialog. So a confirm button is always rendered by the screen that owns the state behind it: there is **no `useDialogFooter`** and no portal into the dialog's footer any more, because there is no footer up there to portal into. A dialog with more than one screen holds a discriminated `Step` union and switches on it once, in a single `renderStep()`: one switch decides the body, the actions and the back arrow together, so they cannot drift out of step with each other the way three parallel conditions did. Seed a screen's state from its props with `useState` initializers — a router only mounts a screen once what it needs has loaded, so there is nothing left for an effect to react to. **Closing is a reset, not a step back**: `DialogButton` calls `onClose` from its own close handlers (the X and the backdrop), never from an effect watching the closed state — that effect re-ran on every render and, once a router set a fresh `{kind: "list"}` object each time, looped until React gave up.
- **Component Style**: Follow the established pattern of using dedicated helper methods (e.g., `handleAction`, `renderContent`, `handleEffect`) within functional components to keep the JSX clean.
  - **Hook Convention**: If a React hook (like `useEffect`, `useMemo`, `useCallback`) is not a simple one-liner, move its implementation to a dedicated function below the `return` statement and name it `handleEffect***`, `handleMemo***`, etc.
  - **JSX in Props**: Never write multi-line JSX directly in component props. Instead, create a dedicated `render***` function (e.g., `renderDescription`) below the `return` statement. One-liner JSX is allowed.
  - **Styles Naming**: Always name the constant for component-specific styles as `SX`. Do not use descriptive names like `VAULT_NEW_SX`.
  - **Shared Styles**: Never share `SX` styles between components. Sharing styles is a signal to create a separate reusable component (e.g., instead of sharing a `code` style, create a `Code` component in `view/box`).
  - **Member Order**: Maintain the following order within functional components:
    1. `return` (JSX)
    2. `render***` methods
    3. `handle***` methods
    4. `handleEffect***`, `handleMemo***`, etc. (specific React hooks)
    5. `get***` methods
- **Cache Management**: Be cautious when updating React Query keys. If a linter warns about a missing dependency that was intentionally omitted to control cache invalidation, use `// eslint-disable-next-line` instead of changing the key signature.
- **TypeScript Nullability**: Never use `null` in TypeScript code; always use `undefined` for representing missing or optional values.

## Backward Compatibility & Persistence
- **Backup Models are Sacred**: Structs used for backups (e.g., `Backup`, `backupCluster`) must remain unchanged in their nomenclature and JSON tags to ensure long-term compatibility. If changes are necessary, a new backup version must be introduced. **A version owns its whole shape — it never borrows the last one's.** `BackupV2` shares no type with `BackupV1`: `backupClusterV2`, `backupNodeV2`, `backupQueryV2`, `backupPermissionsV2` and `backupDeploymentV2` mirror today's root models (`cluster.Response`, `cluster.NodeConfig`, `query.Response`, `permission.UserPermissions`, `deployment.Template`) carrying only what a restore needs, and each version's mappers are its own — `syncPermissionV2` duplicates `syncPermissionV1` rather than calling it, so a frozen version's code never changes because a new one needed something. The V1 shapes exist to *read old files*: they describe an Ivory that knew one engine, so reusing them is how V2 first came to lose the plugin of every cluster and query, every node's name and its db/ssh ports, and (via `exportV1`, which skips them on purpose) every non-postgres query outright. So V2 names the keeper/database pair and the query's engine, keeps `tls` (dropping it would restore a TLS cluster as a plaintext one) and stores its enums **as words** (`"bloat"`, `"granted"`) — V1's ordinals only mean anything beside the list they were written against. What V2 leaves out is what points outside the file: vault and certificate ids, and a query's pre-edit `Default`. Renamed features are still resolved on the way in (`syncPermissionV2` → `config.Feature.Current()`), and a V1 file still restores as patroni over postgres — that mapping lives in `importV1`, the only place that knows what V1 meant. Only `Manual` templates are exported: the shipped ones are computed from the keeper plugins on every request, so exporting one would import it back as an editable copy sitting next to the original. `backupDeploymentCommandV2` carries a `backupDeploymentCommandDefaultsV2` beside the command for the same reason the template does — a file restored without it puts every node of a single-host template back on one port — and `backupDeploymentV2` carries a `backupDeploymentDefaultsV2` of the credential usernames, without which a restored template would open every deploy with its credentials switched off. Neither carries a password. Version detection stays filename-based (`ivory.v2.bak`), with a name carrying no version at all still meaning V1.
- **Internal DB Migration**: Internal database models (e.g., `Cluster` in `features/cluster/cluster_model.go`) can be refactored and their JSON tags updated. The backup tool is the primary mechanism for users to migrate data between versions if the internal schema breaks.
- **Data Integrity**: When renaming internal models, always verify if they are part of the backup/export logic before changing their JSON representation.
- **A Renamed Enum Value Keeps a Forwarding Entry — Only If It Was Ever Written**: `config.Feature` is stored as its *string value* in permission maps and backups, so renaming one silently invalidates every row already written. It owns a `renamedFeatures` map from the old key to the new one and a `Current()` method resolving it (`"view.node.platform"` → `ViewNodeSystem`), and the entry stays forever: it is the migration. Apply `Current()` where stored data enters the code, never scattered at use sites — `permission.PermissionMap.renamed()` (called by `normalizeDatabase`, which runs at startup via `setAuthConfig`) and each backup version's own `backup.syncPermissionV1`/`syncPermissionV2`. The table is guarded by a test asserting every target is itself current and present in `config.All`. **A rename inside a feature that has never shipped needs none of this**: `platform.PluginType` was renamed `"linux"` → `"docker"` while `features/deployment` — the only thing that persists a platform key, along with `BackupV2` — was still unreleased, so there is no stored row to forward and no `platform.PluginType.Current()`. Add a forwarding entry when a released version wrote the old key to disk, not on every rename.

## Testing Guidelines
- **Zero Deletion Policy**: NEVER delete existing tests during refactoring or type synchronization. If types change, UPDATE the tests to match the new structures. A "refactor" that results in fewer tests is a failure.
- **Backend Tests**: Backend tests use Go's standard `testing` package with table-driven tests and `t.Run()` subtests. Test repository methods (storage adapters) and service logic only. Routers are thin request/response glue and are not tested; the http engine's middlewares (auth, logging, etc.) are the exception and can be tested directly. A test file's name must exactly mirror the source file it tests (e.g. `cluster_repository.go` → `cluster_repository_test.go`), never a custom descriptive name (not `cluster_repository_search_test.go`) — if a file already has a `_test.go` counterpart, add to it instead of creating a new one.
- **Frontend Tests**: Frontend tests use Rstest and Testing Library. Tests are colocated with the source files they test, following the pattern `[filename].test.[ext]`. No coverage threshold is defined. Test all unit functions and hooks, and give `shared/` (helpers, hooks, providers) thorough coverage since it's foundational, reused logic. Providers (`shared/provider/*`, e.g. `StoreProvider`, `AppProvider`) are tested despite being React components, because they carry state/context logic rather than presentation. **Do not write tests for presentational React components** (pages, widgets, `shared/component/*`) — skip `*.test.tsx` component tests unless explicitly requested.

## Commit & Pull Request Guidelines
Recent commits use short, imperative summaries such as `add tooltips for refresh buttons` and `fix problem with different column widths in list`. Keep commit subjects concise and specific; add a body when the change needs context. Pull requests should describe behavior changes clearly, link relevant issues, and include screenshots or GIFs for UI work. Before opening a PR, run the relevant backend tests, frontend lint, and affected frontend tests.
